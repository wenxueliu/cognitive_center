# OpenSpec规范驱动开发框架实战指南

## 概述

OpenSpec是一种规范驱动（spec-driven）的开源开发框架，主要面向AI编程助手（如Claude Code、GitHub Copilot、Cursor等）而设计。它通过在「共识规范 → AI执行 → 自动验证」的闭环流程，帮助团队在AI参与的代码开发过程中明确需求、降低指令歧义、提升代码可追溯性与可维护性。

## 核心理念与工作流

### 1. 闭环开发流程
OpenSpec实现了一个完整的规范驱动开发闭环：

```
共识规范（Spec） → AI执行 → 自动验证 → 迭代与归档
```

### 2. 核心工作步骤

#### 步骤1：共识规范（Spec）
- **共同撰写**: 由人类与AI共同撰写结构化的需求规范
- **规范内容**: 包括功能描述、输入/输出、边界条件、测试用例等
- **文档化**: 将需求明确化为可执行的规范文档

#### 步骤2：AI执行
- **自动生成**: AI根据规范自动生成代码、文档或变更提案
- **约束生成**: 确保AI在规范约束内工作，避免随意性
- **结构化输出**: 生成符合项目结构和技术标准的代码

#### 步骤3：自动验证
- **内置验证器**: 框架内置的验证器依据规范中的测试用例进行检查
- **自动化检查**: 对生成的代码进行自动化验证
- **合规性确认**: 确保实现符合预期规范

#### 步骤4：迭代与归档
- **审查流程**: 通过审查、计划、实现、归档等步骤形成完整的变更历史
- **可追溯性**: 便于后续审计与迭代
- **版本管理**: 维护规范的版本历史和变更记录

## 项目结构与配置

### OpenSpec项目结构
```
openspec/
├── specs/                    # 规范目录（存放各类正式规范文档）
│   └── auth/                # 认证相关规范子目录
│       └── spec.md          # 当前认证规范文档（若存在）
└── changes/                 # 变更目录（存放规范的修改提案与增量内容）
    └── add-2fa/             # 新增双因素认证（2FA）的变更子目录（由AI创建完整结构）
        ├── proposal.md      # 变更提案文档（说明为何修改、修改内容）
        ├── tasks.md         # 实施任务清单（记录需完成的具体开发/修改任务）
        ├── design.md        # 技术设计文档（技术方案决策，可选）
        └── specs/           # 变更对应的规范增量目录
            └── auth/        # 变更涉及的认证规范子目录
                └── spec.md  # 规范增量文档（仅展示新增/修改的内容，即差异部分）
```

### 配置文件说明

#### AGENTS.md
- **作用**: 定义AI代理的角色和能力
- **内容**: 包含AI助手的配置和约束条件
- **用途**: 确保AI在项目中有明确的角色定义

#### project.md
- **作用**: 项目的基本信息和配置
- **内容**: 包含项目描述、技术栈、开发规范等
- **用途**: 为AI提供项目上下文信息

## 安装和配置

### 1. 安装OpenSpec

#### 使用npm安装
```bash
npm install -g @fission-ai/openspec@latest
```

#### 使用pnpm安装（Windows推荐）
```bash
pnpm install -g @fission-ai/openspec@latest
```

#### 验证安装
```bash
openspec --version
```

### 2. 项目初始化
```bash
openspec init
```

这个命令会在项目中创建OpenSpec的目录结构，为后续的规范驱动开发做准备。

## 核心工作流程

### 1. 需求收集和整理

#### 流程概述
1. **起草变更提案**: 明确期望的规范更新内容
2. **AI助手审核**: 与AI助手一同审核该提案，直至达成一致
3. **执行任务**: 参考已达成共识的规范文档执行开发任务
4. **变更归档**: 将已批准的更新内容合并回基准规范文档

#### 核心命令
OpenSpec主要通过三个关键命令来管理工作流：

##### /openspec:proposal
- **功能**: 起草变更提案，将需求转化为详细的计划和任务
- **输入**: 需求描述和相关资料
- **输出**: 包含tasks.md的完整提案文档
- **作用**: 防止AI随意编写代码，确保有明确的约束和计划

##### /openspec:apply
- **功能**: 执行已通过提案的任务清单
- **依据**: 严格按照tasks.md文档执行
- **过程**: 代码编写、测试、验证等
- **约束**: 遵循规范文档的约束

##### /openspec:archive
- **功能**: 对完成的变更进行归档操作
- **目的**: 便于后续的审计和追溯
- **操作**: 将变更合并回基准规范文档
- **结果**: 形成完整的变更历史

## 实战案例分析

### 案例背景
以jimeng-free-api-all项目为例，演示如何使用OpenSpec实现即梦4.0文生图功能扩展。

### 1. 项目准备
```bash
# 下载项目
git clone https://github.com/zhizinan1997/jimeng-free-api-all

# 初始化OpenSpec
openspec init

# 配置项目（翻译配置文件为中文）
```

### 2. 需求提案
#### 需求描述
基于curl4.md内容以及现有的images.ts代码，新增high_aes_general_v40模型支持，包括：
- 文生图功能
- 图生图功能  
- 文生视频功能

#### 提案生成
使用`/openspec:proposal`命令生成详细的提案文档，包括：
- **proposal.md**: 变更提案说明
- **tasks.md**: 详细的实施任务清单
- **design.md**: 技术设计文档

### 3. 任务执行
#### 自动化任务分解
生成的tasks.md包含12个具体任务：
1. **模型支持实现** - 在MODEL_MAP中添加jimeng-4.0模型映射
2. **参数优化** - 支持更高的分辨率配置
3. **批量生成** - 优化generateImages函数
4. **测试验证** - 单元测试和集成测试

#### 执行过程
使用`/openspec:apply`命令执行任务清单，AI会：
- 严格按照tasks.md执行
- 逐项完成任务并标记完成状态
- 生成符合规范的代码
- 进行自动化测试

### 4. 人工验证
#### 代码审查
- 检查修改的代码是否符合预期
- 验证功能实现是否完整
- 确认代码质量和风格一致性

#### 接口测试
- 使用Apifox等工具进行接口测试
- 验证API返回结果
- 确认与即梦平台的对接正常

### 5. 归档操作
使用`/openspec:archive`命令将完成的变更归档：
- 合并到基准规范文档
- 形成变更历史记录
- 便于后续审计和追溯

## 适用场景分析

### 1. 新项目开发
- **优势**: 从项目开始就建立规范体系
- **价值**: 确保项目从一开始就有清晰的规范约束
- **适用**: 对代码质量和可维护性要求高的新项目

### 2. 功能增强（迭代项目）⭐
- **核心价值**: 解决AI在老项目上下文理解的问题
- **场景**: 基于现有项目扩展和改造
- **优势**: 通过规范文档为AI提供充分的项目上下文

### 3. 多人协作开发⭐
- **核心价值**: 解决AI开发项目中多人协作的难题
- **场景**: 大型团队的AI辅助开发
- **优势**: 通过统一的规范确保团队协作的一致性

## 技术优势分析

### 1. 解决模型上下文限制
- **问题**: AI工具在处理大型企业项目和老项目改造时缺乏充分上下文
- **解决方案**: 通过结构化规范文档为AI提供完整的项目上下文
- **效果**: 显著提升AI在企业级项目中的适用性

### 2. 提升多人协作效率
- **问题**: AI开发项目中团队协作困难，缺乏统一标准
- **解决方案**: 通过规范文档建立团队的共同语言和工作标准
- **效果**: 提升团队协作效率，减少沟通成本

### 3. 降低代码随机性
- **问题**: AI生成的代码存在随机性和不一致性
- **解决方案**: 通过tasks.md任务清单和验证机制约束AI行为
- **效果**: 确保代码质量和一致性

### 4. 增强可追溯性
- **问题**: AI生成的代码缺乏变更记录和审计追踪
- **解决方案**: 完整的提案-执行-归档流程
- **效果**: 便于项目管理和质量审计

## 与其他工具的对比

### vs GitHub Spec Kit
- **OpenSpec**: 更强调AI代理的约束和自动化执行
- **GitHub Spec Kit**: 更侧重于规格文档的版本控制和协作

### vs Claude Code规格工作流
- **OpenSpec**: 提供完整的项目管理框架
- **Claude Code**: 更侧重于命令行的规格操作

### vs 传统项目管理
- **OpenSpec**: 专为AI辅助开发设计，提供AI约束机制
- **传统项目管理**: 缺乏对AI工具的特殊支持
